## 名前と免許

**aiseed office(仮称)。** 「japanese-office」をやめたのは、
日本語が特別なのではなく**日本語が第2の型の言語の一例**だから。
`lang` の `Language` を1つ足せば各国語版になる形にしてある。

免許は **AGPL-3.0-or-later**。理由と代償は `NOTICE.md` に書いた。
要点だけ: **クラウドの役務として提供されたときに原本が渡らない穴を塞ぐ**ため。
大手のソフトに取り込まれる道は捨てる — 取り込まれるのではなく、置き換える。

`ribbon.rs` は Euro-Office(AGPL-3.0)の翻訳の派生物なので、由来の表示が要る。

### なぜ堀を越えられたか — VBA の前提の崩し方(2026-08-04 発注者の振り返り)

Microsoft の堀は「**競合には VBA が作れない**」だった。実際、互換で挑んだ
ものは全部この堀に落ちた — 30年物の実行系のバグまで含めた再現は終わらない
仕事で、追いつく頃には本家が先にいる。

崩し方は互換ではなく**置き換え**だった。堀の実体は VBA という言語ではなく
「**コードが帳票と一緒に旅をし、ファイルコピーで配れる**」という性質で、
それは joPython.xml が再現した。しかも本家が構造的に直せない欠陥
(開く=実行、檻なし)を**最初から持たずに**。言語は Python — VBA より
広い公共財(polars・scipy・matplotlib)ごと手に入り、書ける人も多い。

これを可能にした技術の柱が2本:

- **Rust で書いたこと。** 核(kumihan / sheet)が UI から独立した安全な
  部品になり、GPUI で速さは構造から出る。そして **PyO3** — sheet を
  そのまま Python の束縛(pysheet / office_sheet)にする橋が安く架かった。
  「Rust が帳票の形を守り、Python が中身を作る」分業は、この橋の安さが
  前提。グラフ・ピボット・ソルバー・方程式が日単位で入ったのは、
  重い仕事を Python の公共財に投げ、Rust 側は釦と檻だけ持ったから
- **AI(Fable)が開発者だったこと。** この構え(小さい Rust の核+
  釦の裏の Python+檻)は、1釦=1台本+結線という**小さく検査できる
  単位**の積み重ねで、AI の開発と相性がよい。発注者+Fable 2人で
  この速度が出たのは偶然ではなく、構造の帰結

残りの正直な注記: 堀を越えたのは**構造**で、現場の移行には既存 VBA の
移し替えの手間が残る — **これも AI の仕事にする**(発注者 2026-08-04。
下の「AI メニュー」の節)。

### AI メニュー(2026-08-04 発注者確定)— 「AI タブは作らない」の改訂

当初は「校正は AI 機能ではなく普通の機能 → レビューに置き、リボンに
AI タブは作らない」(校正の節)。**校正をレビューに置くのは不変**のまま、
改訂する: **ONLYOFFICE と同じく AI タブを両アプリに作る**。置くのは
言語の普通の機能ではなく、**モデルに任せる変換と生成の道具箱**:

- **第1号: VBA の移し替え(calc)** — 「現場ごとの既存 VBA の移し替えは、
  Claude の仕事」(発注者)。xlsm の vbaProject からコードを取り出し
  (裏方は oletools = Python の公共財)、モデルが **Python in Calc の
  台本へ**書き換えて `@save` の形でブックに載せる。**人が読んで確かめて
  から使う** — 変換結果が自動で走ることはない(開く=実行なしの規律は
  ここでも破らない)。元の vbaProject は消さない(原文持ち越し —
  移し替えが疑わしければいつでも見比べられる)
- writer 側の候補: 要約・書き換え・翻訳・ふりがな(--washi の資産)。
  calc 側の候補: 式の説明・自然言語→式。中身は使いながら決める
- **宛先の規律**: 既定は**ローカル**(校正と同じ OpenAI 互換の口 —
  基幹網の外に出ない)。Claude API 等の外部へ出すのは**設定で明示した
  ときだけ**(コードや文書を外に出すかは現場の判断。鍵がブックや文書に
  入ることは決してない)。繋がらなければ「できません」と言う —
  黙って空の結果にしない(校正と同じ)
- **改訂(2026-08-04 発注者「API でなくて定額サブスクでも大丈夫なように」)**:
  宛先を3つにした(`lang::ai::Backend`)。**②が定額の契約で使う道**:
  ①**手元のモデル**(既定。外に出ない)②**Claude(定額)**= 手元の
  `claude` コマンド(Claude Code の CLI)を子で呼ぶ — **API の鍵は要らず**、
  CLI が持っている認証をそのまま使う ③**Claude(API)**= 鍵は環境変数
  `ANTHROPIC_API_KEY` からだけ読む。選んだ宛先は
  `~/.config/office/ai.txt` に覚える(`JO_AI` が優先。鍵は決して書かない)。
  CLI を呼ぶときは **道具を与えない**(`--allowed-tools` を空)= 手元の
  ファイルを触らせず、文書の中身は標準入力で渡す(コマンド行に載せない)。
  claude が見つからなければ入れ方を添えて断る
- 実装は各アプリ側 — VBA の移し替えは calc(この環境)の受け持ち

### calc の AI タブ(2026-08-04 実装)

writer と**同じ10釦・同じ宛先**(`ui::ai`)。違いは渡すもの・返すもの:
表計算なので**選択範囲の TSV を渡し、TSV や式で受ける**。反映は必ず
checkpoint してから = **Ctrl+Z の1手で戻る**。保護中は断る。CalcAi:

- **宛先** — writer と共通(手元 → Claude 定額 → Claude API)
- **要約** — 選択(無ければ使っている全域)の表を2〜4文に。カーソルの
  **コメント**へ付ける(保存で xlsx に残る)
- **書き直す・敬語にする・やさしく** — 同じ形の TSV を受け、**文字の
  セルだけ**置き換える(数字と式は触らない)。行数が合わなければ断る
- **翻訳** — 同上(日本語⇄英語)
- **ふりがな** — 1列を選ぶと、読みを**右隣の列**へ(名簿のフリガナ欄。
  右隣に中身があれば断る)
- **続きを書く** — 選択のパターンから続きの行を作り、下の空きへ
  (中身があれば断る。「AI の当て推量、よく確かめて」と言う)
- **表にする** — 板に文章を打つと、表にしてカーソルから流し込む
- **頼む** — 板に用件。**= で始まる答えは式としてカーソルへ**
  (数式を頼める)、他はコメントへ。式に使える関数を system で教える
- 行数の食い違い・空きでない置き場は**断る**(黙って潰さない)

### writer の AI タブ(2026-08-04 実装)

10 の釦。**どれも「返事をどう使うか」まで決めてから頼む**(使い道の
決まっていない答えは受け取らない)。反映は必ず doc_undo に控えるので
**Ctrl+Z の1手で戻る**。保護中は断る。

- **宛先** — 押すたびに 手元 → Claude(定額)→ Claude(API)と回り、
  使えない宛先なら理由をその場で言う
- **要約**(頭に【要約】として置く)・**書き直す**・**敬語にする**・
  **やさしく**(選択を置き換え)・**翻訳**(日本語⇄英語)・
  **続きを書く**(カーソルの後ろへ)・**表にする**・**頼む**(自由な用件)
- **マクロを書く**(11個目 2026-08-05)— 用件を板で聞き、モデルに
  **台本の作法を system で教えて**(fill/extract/fields/render だけを使う・
  ラベル走査をしない・表は rows でなめる・print で報告・SystemExit で断る)、
  文書の**記入欄の名前一覧を的として渡す**。答えは文書に入れず
  **~/.config/office/plugins に .py で置くだけ** — 人が読んで確かめてから
  プラグイン一覧で実行する(開く=実行なし・変換結果は自動で走らない、の
  規律は VBA の移し替えと同じ)。コードフェンスは受け側でも剥がす
- **ふりがな** — K4 のルビが効く場所。モデルには `|語《よみ》`(pywashi と
  同じ記法)で返させ、writer が記法をほどいて**うちのルビ**として振る。
  文字は1字も変わらない(記法が壊れていても本文を落とさない試験つき)

### K4 の見立て — 縦書き・ルビ・均等割付は作れる(2026-08-04 発注者)

発注者「作れるでしょう」— 同意。ソースで裏を取った現在地と道順:

- **土台は最初から用意してある。** kumihan の冒頭に「縦書き・ルビ・
  均等割付・ぶら下げは K4(モデルはそれを妨げない形にする)」と宣言済みで、
  核は「置かれた文字の座標」を返すだけ — 画面・PDF は写すだけなので、
  組みの拡張は核の中に閉じる
- **① 均等割付(いちばん近い)**: `Align::Justify` は enum も docx 往復
  (`both` / `distribute`)も**既にある**。無いのは描画の字間配分だけ
  (今の Justify は左寄せと同じに描いている)。実装は「禁則で折った後の
  行の余りを字間に配る」一つの関数 — 和欧の境や約物の前後の配り方
  (JIS X 4051)は段階的に細かくすればよい。段落の distribute と、
  run 単位の「◯字取り」(docx の w:fitText)は同じ道具の2つの使い口
- **② ルビ**: docx の `w:ruby`(rubyBase + rt)の読み書きと、**半分の
  大きさの副行**を親文字の上に置く組み。読みが親より長いときの配りは
  ①の字間配分がそのまま道具になる。行の高さはルビの分だけ持ち上げる。
  そして**読みの自動付与は既に資産がある** — furigana の道具と
  青空文庫での実測(読みが割れる語 561種)。Word の「ルビ」より良いものに
  できる場所(ローカルのモデルが文脈で読みを選ぶ)
- **③ 縦書き(いちばん重い・いちばんの存在理由)**: 行組みは1次元の
  詰め込み問題なので、**軸の入れ替え**で核の禁則・字幅の道具は全部
  生き残る。新しく要るのは (a) 約物の縦書き字形(、。ー「」等 —
  OpenType の vert。無ければ常用の約物だけの対応表で始める家風)、
  (b) 欧文の回転と**縦中横**(2桁の数字を横に寝かせる — ②の副行と
  親戚の「行の中の小さな別軸」)、(c) 段=列が右から左へ進む紙面。
  docx とは sectPr の textDirection(tbRl)で往復
- **順序が道具を作る**: ①の字間配分 → ②の副行と字取り → ③の軸の
  入れ替え、と各段が次の材料になる。実装は writer / engine 側(相方)—
  受入の物差しは「JIS X 4051 に従う縦組みの実物(通知文・賞状の類)が
  画面と PDF で同じに組めること」

### pywashi との関係 — K4 の教師と、記法の合流(2026-08-04 発注者)

[pywashi](https://github.com/aiseed-dev/pywashi)(発注者の既存プロジェクト。
MIT)は「Markdown から美しい日本語文書(HTML / PDF)を作る `washi`」で、
**K4 が目指すものが既に動く形である**: 禁則・約物の行頭詰め・句読点の
ぶら下げ・両端揃え・段落頭一字下げ、ルビ(でんでん記法 —
グループ `{漢字|かんじ}` / モノ `{東京|とう|きょう}`)、縦書き
(`--vertical` 右→左)、原稿用紙(`--genko`)、傍点・傍線。
PDF は Chrome ヘッドレスで刷る。ここから4つ:

- **K4 の教師・受入手本**: 縦書きとルビの「あるべき見え方」の現物。
  kumihan の K4 は**同じ原稿を washi と組み比べる**のが検査になる
  (Euro-Office を「挙動の教師」にしたのと同じ作法)
- **記法の合流**: `office-spell --washi` は既に pywashi 記法で吐く。
  writer の「ファイルからのテキスト」(.md)がでんでんのルビ記法を
  受ければ、**ふりがな付与 → ルビ入り文書**が一本の道になる —
  K4 ②ルビの入り口として、docx の w:ruby と並ぶ2つ目の口
- **HTML 読みとの噛み合い**: washi の出す自己完結 HTML は writer の
  HTML 読みの上等な実物試験(受入 09 の `<ruby>` は当面「文字を拾う」
  扱い — K4 ②が入ったら「ルビとして組む」へ格上げ)
- **住み分けと将来**: washi は Markdown→紙(Chrome 依存)、office は
  docx/xlsx の編集(Chrome なし)。kumihan が縦書き・ルビを持てば
  同じ品質が Chrome なしで出る — washi のレンダラを kumihan で
  置き換える道もあり得る(いまは教師として使う)

**発注者の意向(2026-08-04):「pywashi の Rust 版ができるといい」。**
実現の形は**新しい製品を作ることではない** — K4 が済めば、部品は全部
この家にある:

- 組み(禁則・ぶら下げ・ルビ・縦書き・均等割付)= **kumihan の K4 そのもの**。
  原稿用紙は「1字1マスの字取り」= 均等割付の親戚。傍点(圏点)も
  JIS X 4051 の内 — K4 の道具立てに足す
- 入り口 = **でんでん記法の .md 読み**(writer の「ファイルからのテキスト」
  の延長。ルビ {漢字|かんじ}・傍点 [〜]{.sesame_dot} を受ける)
- 出口 = **paper の PDF**(Chrome 不要 — ここが washi に対する最大の進歩)。
  washi 流の既定(明朝・両端揃え・一字下げ・行間)はテーマとして持つ
- 形は2つ、掟と整合する: **writer で .md を開いて刷る**(製品は増えない)/
  画面なしの **CLI の道具**(office-spell の前例 — 「製品ではなく道具」は
  バイナリ2本の掟の外)。青空文庫17,000作の組版試験のような「測る仕事」は
  CLI が要るので、両方作るのが自然

順序は変わらない: K4(均等割付→ルビ→縦書き)が先で、washi 相当は
その**果実**。教師(washi)と組み比べて合格したものが、そのまま後継になる。

**pykobo は畳める(2026-08-04 発注者「もうこれが不要になるでしょう」)。**
[pykobo](https://github.com/aiseed-dev/pykobo)(AISeed工房 — 青空注記 /
AsciiDoc で書き、washi で縦書きを確かめ、紙とデータに出す Flet アプリ。
「昔の日本語ワープロの現代版」)の中核は、K4 済みの writer がそのまま担う:

| pykobo | office での姿 |
|---|---|
| 執筆+ルビ・傍点の付与 | writer(K4 ②ルビ・圏点。付与の裏はふりがなの資産) |
| 組版プレビュー(washi / Chrome) | **プレビューという概念ごと消える** — writer は画面=紙 |
| 印刷・PDF | paper(Chrome 不要) |
| 表を xlsx から | calc がいる(同じ家) |
| 校正(Claude API・鍵が要る) | writer の校正(**ローカルのモデル** — 鍵不要・基幹網の外に出ない。上位互換) |
| Web 版(LAN 共有) | 別 UI は作らない(必要なら閉域 Web の路線で) |

**残差はプラグインにする(2026-08-04 発注者確定)。**
青空注記の読み・EPUB 書き出し・TTS・VLM 書き起こしは、本体に入れず
**プラグイン(`~/.config/office/plugins` の .py・檻の中で実行)**として
提供する。これで置き場の議論が全部消える:

- **本体の範囲は動かない**(出口は docx / PDF のまま)。広げるのは
  プラグイン — バイナリは増やさず、範囲の外の仕事は檻つき Python へ
- **Python の資産をそのまま使う**(pybunko・ebooklib の類。Rust に
  移植しない — 公共財が既にあるところには作らない、の原則どおり)。
  pykobo の解体は「Flet の UI を捨てて、中身を plugins/ に移す」だけ
- プラグイン機構は writer・calc 両方に**もうある**。エクスポート型
  (EPUB のように檻の中で作った成果物を、利用者の選んだ場所へ写して
  渡す作法)だけ実装時に確定する — 相方への申し送り
- コードの配布路はこれで3つに揃う: **ブック搭載**(@save・網なし檻)/
  **ページ搭載**(script type="py"・檻)/ **プラグイン**(手元の
  ~/.config・檻)。どれも Python・どれも檻・どれも開く=実行なし

畳む順序: K4 → 青空注記のプラグイン → それで pykobo の日常の仕事が
